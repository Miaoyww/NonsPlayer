# 音乐库首页点歌响应与旧请求抢播调查

日期：2026-10-12。本文保留修复前的调查结论；后续已按用户指示实施修复。

## 已实施的修复

- 整组请求立即进入音频 actor，由 actor 管理单个准备任务及请求代次；旧任务取消和迟到结果校验共用该入口。
- 已知曲目先加载并播放，歌单后台补齐，保留进度和音源；队列编辑选择保留用户修改，取消待补齐任务。
- 无已知曲目的整组播放立即显示 Loading，获取期间能够被其他播放命令替代；补齐前复核来源/账号作用域。
- 首页允许加载期间改选，旧请求的错误和提示不覆盖新请求；当前曲目加载状态使用 shadcn Spinner 的 CSS 旋转动画，屏幕阅读器仍能读取“正在加载”，视口外或减少动态效果时停止动画。
- 临时单曲队列补齐前不做无缝预加载，避免随机/循环模式预先绑定错误的下一首。
- 网易云每页重复读取歌单详情的性能优化尚未实施；它已不阻塞首页已知歌曲起播。

回归测试位于 `app/src-tauri/src/playback/collection.rs` 和 `app/tests/library-playback-selection.test.mjs`。原始一次性 IPC 复现脚本在完成调查后移除；下文运行命令和失败记录描述修复前的受控实验。

## 结论

这是播放入口编排与播放核心之间的设计缺口，并有页面反馈不足放大问题。当前播放核心并非完全没有取消机制：它已有异步音源解析、任务取消、generation 校验及 Loading 快照；但是这些机制在完整歌单准备完成、Queue 命令进入核心之后才生效。用户的新选择发生得更早。

不能只用防抖、禁用按钮或增加 spinner 解决：它们既不能使核心知道新选择，也不能阻止其他页面或入口的迟到请求替换队列。

## 实际路径

1. 首页歌曲点击调用 `music-library.tsx` 的 `playCollection(liked, track.key)`。该页面已有 Track 元数据，但这里只传歌单 ID 和歌曲 key。
2. `playLibraryCollection` 发起 `play_library_collection` IPC，不经过前端读取缓存。
3. IPC 首先等待 `music.library_queue` 获取完整播放歌单。最多串行读取 10 页、1000 首，总预算 12 秒。
4. 网易云适配器每页读取歌单详情，再读取该页歌曲详情；当前循环每页都再次读取歌单详情。该准备工作发生在音源解析之前，不代表不可避免的首声延迟。
5. 直到所有页完成、保存歌曲后，IPC 才发送 `Command::Queue`。此时核心更新所选曲目、取消旧音源任务、发出 Loading 状态并解析音源。

因此“点击一首已展示的歌曲”被不必要地绑定到“获取完整歌单成功”。界面查询缓存命中不能自动避免这个后端整组查询。

## 用户描述的时序

```text
点击 A → 等整份歌单 → Queue(A) → A 的音源解析中
                                  ↓ IPC 返回，首页解除 playing 禁用
点击 B → 再等整份歌单……           → A 解析成功并开始播放
        → Queue(B)                → 核心这时才取消 A、加载 B
```

B 的点击已发生，但在 B 的歌单准备完成前，核心还认为 A 是有效的最新请求。所以 A 出声后又立刻切 B，可以由现有流程直接解释，不需要假设 GStreamer 忽略了取消。

还有更严重的变体：两个整组请求重叠且乱序返回时，较早点击的 A 可以在 B 之后发送 Queue，覆盖新的选择。核心看到的是完成顺序；现有音源 generation 无法识别该 Queue 原本属于旧点击。

## 反馈问题

首页 `playing` 是“整组 IPC 未返回”，并非音频正在播放，也不是“哪个歌曲正在加载”。获取期间只禁用多个歌曲按钮，没有绑定目标歌曲的加载状态。`data-current` 与 PlayingIndicator 来自核心快照，核心未收到 Queue 前不会反映点击目标。

首页用 React state 阻止重复操作，没有同步 ref 锁；同一批 React 更新前的快速调用可能绕过检查。即使增加 ref 锁，也只解决局部重入，不能解决上述正常先后点击或跨入口迟到结果。

## 受控复现

运行：

```powershell
node docs/investigations/reproduce-collection-playback.mjs
```

脚本读取当前 `application/mod.rs` 中实际的 `play_library_collection` 函数体，使用 rustc 编译，替换外部依赖为可手动完成的网络 future、无操作存储和记录命令的 Player。A/B 来自同一个歌单，替身返回包含两首歌的相同队列。

四项期望均失败：

- 点击后、歌单仍在准备时，尚无任何命令进入 Player。
- A 已进入音源解析阶段，B 点击并等待歌单时，尚无取消 A 的命令。
- A/B 都在准备歌单时，A 仍可在 B 点击之后提交播放。
- B 先完成、A 迟到时，最终提交的选曲是 A，期望应为 B。

该复现覆盖真实 IPC 函数的异步边界和命令提交顺序；没有启动真实音频、SMTC 或网络。没有测量用户机器上的 1–2 秒耗时，也不能据此宣称音频线程绝无其他延迟。

## 排查判断

| 候选原因                                   | 证据与判断                                                                                                                         |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| 歌单准备先于播放意图登记，旧整组请求不失效 | 受控测试直接证实，是本轮确定的根因                                                                                                 |
| 播放核心没有取消音源任务                   | `load_at` 调用 `cancel_jobs`，后者推进 generation 并 abort 任务；Resolved 分支拒绝旧 generation，现有代码不支持此说法              |
| 音频线程被网络解析阻塞                     | `resolve` 在异步任务中调用 MusicService，不同步等待网络；未实测 GStreamer 状态切换或 SMTC 本地封面同步的耗时，不能排除独立阻塞问题 |
| 仅缺少点击反馈                             | 页面确实没有目标歌曲的加载反馈，但不能解释或修复旧整组请求抢播                                                                     |

## 根治的实现边界

应该把“用户要求播放什么”与“为播放准备队列和音源”分开，由共同的播放请求入口管理，而不是给各个页面复制锁。

1. **在任何异步准备之前登记新播放意图。** 统一生成请求代次；Player 接受意图时立即让旧队列准备、旧音源解析及旧预加载失效。直接播放、整组播放、队列跳转、私人 FM、插件发起播放及停止/清空都必须明确对该代次的影响。
2. **已知目标曲目先进入 Loading。** 首页已有歌曲信息，可经存储核对后立即交给核心解析和播放，完整歌单准备在后台独立进行。单首起播不应依赖完整歌单所有页成功。
3. **后台补齐歌单必须携带原意图代次。** 应用前重新核对目标曲目、来源/会话作用域与最新意图；过期结果和错误都丢弃。补齐时按歌曲 key 重定位索引，保持当前音源、进度和播放代次，不重新起播、不覆盖期间的用户队列编辑。整组读取失败时保留当前可播放曲目，并给出可重试提示。
4. **界面展示目标歌曲及加载状态。** 点击后立刻识别所选歌曲；加载期间仍能改选，新选择替代旧选择。IPC 确认表示“已受理”，不能假装成“已出声”；音频状态继续以核心为权威。
5. **减少冗余整组读取。** 网易云同一次歌单准备获取一次有界 ID 快照，再按需批量补齐元数据；继续核对来源/账号代次，复用现有缓存及失效规则，不缓存临时播放 URL。此优化降低准备成本，但不是竞态修复的替代品。

实施前需要决定整组补齐与用户增删队列的冲突规则，并在播放核心落地测试接口；不能只用本报告中的命令记录替身宣称真实音频已验证。

## 修复验收场景

- A 的歌单或音源挂起，点击 B：B 立即成为加载目标，A 迟到不能启动或恢复音频。
- A/B/C 以不同顺序完成：仅最新有效意图可以提交队列、音源、错误和系统媒体状态。
- 整组准备期间从另一页面直接点歌、点下一首、停止或清空：旧结果不能恢复旧队列。
- 切换账号、停用适配器或退出来源：旧查询和音源不发布。
- 歌单补齐失败：已选曲目仍可播放；成功补齐不重播、不重置进度、不抹掉用户队列编辑。
- 连续点击同一曲目、随机播放、单曲循环和私人 FM：行为定义明确，维持队列上限及无缝交接规则。
- Windows 实际音频验收和 SMTC 验收；耗时报告区分点击到状态反馈、点击到首声与完整歌单准备时间。
